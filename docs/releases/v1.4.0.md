# DeployWhisper v1.4.0

DeployWhisper v1.4.0 expands the v1.3.0 context and scanner foundation with a
governed Skills catalog, structured agent review output, optional integration
policy controls, and stronger credential and release-integrity boundaries.
The UI, API, and CLI continue to share one local-first analysis core.
Canonical reports remain advisory, with deterministic evidence supporting
severe findings and a human responsible for deployment decisions.

## Skills catalog and authoring

- Manifest v1 adds versioned metadata, supported toolchains, scenario and
  documentation references, token budgets, and explicit `experimental`,
  `verified`, `core`, and `deprecated` trust classifications.
- Registry endpoints expose catalog metadata, raw Markdown, SHA-256 checksums,
  and deterministic harness results. Verified and core Skills require passing
  trigger, guidance, evidence, and negative safety scenarios; the harness
  checks context selection and output without executing Skill prose.
- `deploywhisper skill install`, `update`, `remove`, and `list` manage local
  custom Skills. A configured local source supports private and air-gapped
  workflows; registry installs validate the manifest and checksum. Local
  source reads reject symlinks, special files, path escapes, and oversized files.
- The React Skills browser and CLI catalog show trust/source labels,
  deprecation warnings, install counts, test pass rates, freshness, and active
  issue counts from the shared analytics snapshot.
- Contribution guidance, reviewer routing, changed-Skill CI checks, and
  registry publication workflows support maintained community contributions.

See the [Skills authoring guide](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/skills/authoring-guide.md),
[installer guide](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/skills/installer-cli.md),
and [contribution workflow](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/contributing/skills.md).

## Agent review and AI safety

- `deploywhisper analyze --agent-json` emits a stable v1 contract with evidence,
  findings, confidence, uncertainty, context TODOs, and verification guidance.
  Explicit non-approval fields preserve human control.
- A bounded HTTP agent interface submits artifacts and retrieves scoped reports
  through the shared core. Responses declare output limits and truncation;
  consumers must inspect the canonical report when material output is omitted.
  This release provides an HTTP equivalent for agent tooling, without a native
  MCP listener.
- Artifact provenance distinguishes human-authored, AI-assisted, and unknown
  inputs with separate certainty. AI-assisted labels increase review attention
  without creating findings or changing evidence-backed severity.
- Prompt-injection regression gates and threat-model guidance cover untrusted
  artifacts, Skills, incident/scanner content, and provider output. Narrative
  failure preserves deterministic analysis and exposes degraded status.

Read the [agent interface contract](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/ai-safety/mcp-server.md)
and [AI-assisted review guide](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/ai-safety/reviewing-ai-generated-iac.md).

## Optional policy interpretation

Project defaults and integration overrides now configure policy thresholds,
reporting defaults, and `advisory`, `warn`, `soft-block`, or `hard-block` modes.
The separate adapter/enforcement decision leaves canonical reports advisory.
Consumers must use that decision rather than infer enforcement from scores or
narrative text. Missing or invalid decisions are operational failures.

Blocking requires a compatible, pinned consumer and trusted identity,
complete intake coverage, current settings, and human-owned protection and
exception controls. Server settings alone do not establish those controls or
upgrade an older external Action. Review the
[enforcement guardrails](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/enforcement-guardrails.md)
before enabling a blocking mode.

## Credential boundaries and security hardening

- Provider administration validates and persists non-secret profiles. A key
  entered in Settings is transient and used only for the immediate validation
  request; later analysis resolves credentials from the process environment.
- Shared screening protects artifact batches, sibling metadata, structured
  model summaries, report persistence, and configured console logs. Sensitive
  model responses and snapshots are blocked with visible warnings.
- Connector safeguards cover Terraform sensitivity metadata, Kubernetes
  credential references, incident/scanner ingestion, scope errors, OAuth and
  GitHub transport. Credential-bearing URLs and unsafe redirects are rejected;
  public failures omit upstream bodies and credential-bearing diagnostics.
- Share passwords use salted PBKDF2-HMAC-SHA256 with 600,000 iterations.
  Redaction fixes bound malicious-input regex behavior and preserve generated
  `[REDACTED]` markers, including the retained synthetic fuzz regression.
  Query and authorization scans also handle malformed large inputs in linear
  time while preserving sensitive-name normalization and quoting. Artifact
  storage path/symlink checks and webhook error handling are hardened.
- Python, JavaScript/TypeScript, and Actions CodeQL scans, OpenSSF Scorecard,
  scheduled dependency updates, dependency audits, and pinned Actions strengthen
  delivery checks. Frontend dependency remediation removes the affected-version
  matches documented in the security audit; audit results remain time-bound.

## Release integrity and publication gates

The release pipeline builds an exact-commit source archive, `SHA256SUMS`, and
`source-manifest.json`, with a native signed provenance bundle retained as
`artifact.intoto.jsonl`. It verifies subject hashes and repository, signer
workflow, source ref, and commit identity. The container pipeline smoke-tests
the candidate digest and verifies its OCI provenance before promoting version
and stable aliases. Publication refuses existing versions and rechecks tag
identity rather than replacing published assets.

Stable publication is gated on version/source validation, tests, security
checks, source provenance verification, and candidate image smoke/signature
verification. Verify downloaded assets and the exact image digest against the
trusted release tag and workflow identity before using them.
Follow the [artifact verification guide](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/security/release-artifacts.md)
and [release-integrity record](https://github.com/deploywhisper/deploywhisper/blob/v1.4.0/docs/security/release-integrity.md).

## Validation

Release preparation on 2026-10-07 passed full local CI (1,845 tests), root
smoke (555 tests), the API/CLI/infrastructure shard (492 tests plus 257 subtests),
and the full release suite (1,844 passed, one optional skip, 1,318 subtests;
95.18% coverage against the 60% gate). Frontend typecheck, 56 unit tests and
production build passed. All 17Playwright checks passed against a freshly
built Compose application with disposable storage; the original local app and
data were preserved. Ruff lint/format, clean migration upgrade and Python/root/
frontend dependency audits passed. The tagged workflow independently repeats
its blocking test/security/signature/container gates before publication.

## Upgrade notes

1. Back up the database and apply Alembic migrations before using an existing
   installation: `python -m alembic -c alembic.ini upgrade head`. Migration
   `028_add_narrative_guidance_payload` follows v1.3.0 migration 027 and persists
   narrative verification guidance.
2. Configure provider keys in the environment: `OPENAI_API_KEY`,
   `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`/`GOOGLE_API_KEY`, `OPENROUTER_API_KEY`,
   `GROQ_API_KEY`, or `XAI_API_KEY`; `LLM_API_KEY` is the fallback. Restart the
   process/container after changes. Saving settings removes legacy key rows for
   the saved profile and active settings; it does not migrate keys into secrets.
3. Review and clean historical sensitive database rows, snapshots, topology
   mirrors, logs, and backups, and rotate exposed credentials. New screens and
   best-effort legacy-read redaction do not erase previously retained material.
   Screening is defense in depth and cannot identify every secret or encoding.
4. Lint custom Skills against manifest v1 before installing or updating them.
   Strict installer/registry validation may reject older lightweight manifests
   even where runtime loading remains backward compatible.
5. Python metadata supports `>=3.10`; the tested CI/container runtime is 3.11.
   Install the committed hash-locked requirements using
   `pip install --require-hashes --only-binary=:all: -r requirements.txt`
   (`requirements-dev.txt` for development).
6. Existing shared-report password hashes remain usable and upgrade after a
   successful password authentication or reconfiguration. Untouched legacy
   hashes are not bulk-rewritten; reconfigure sensitive shares to upgrade them
   proactively.

For fully local model processing, use a controlled Ollama endpoint and Local-only
mode. Disabling narration alone does not disable all model-assisted assessment.
Shared installations must protect trusted project identity headers behind an
authenticated proxy; caller-supplied scope headers are not authentication.
