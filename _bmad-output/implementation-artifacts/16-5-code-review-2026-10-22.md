## CR16.5-01 — High: stop orphaned workers before replacing their generation

Location: `infra_automation/coordinator.py:511` (recovery),
`infra_automation/local_workers.py:267` (per-process ownership/slot accounting).
AC4/AC7 require at most two analysis workers; AC6 requires owned work to remain
cancellable after recovery.

A successor treats every claimed/running attempt absent from its in-memory
`workers.handles` as abandoned. It marks the old attempt failed and immediately
starts a new attempt. Crashing the coordinator does not terminate its spawned
workers: they establish their own process groups and have no parent-death
supervision. Fencing prevents stale database writes, but it does not terminate
the old handlers or account for their still-live resource use. A successor also
cannot cancel these old workers through its empty ownership collection.

Real process reproduction: start two actual spawned handlers that sleep 90 seconds;
terminate their coordinator with `os._exit(79)`; wait 31 seconds for lease expiry;
start a successor. Both old handlers and two replacements were simultaneously
alive. Observed generation 2 with two new handles; generation-1 attempts were
failed, generation-2 attempts running. All four handlers wrote a PID marker after
entering the handler. Explicitly created process groups were cleaned up afterward.
Scratch probe: `/private/tmp/s165_orphan_probe.py` (exploratory, not a CI test).

Required fix: ensure worker/process-tree lifetime and slot ownership survive or
terminate safely on coordinator death. Confirm old execution is stopped, or
continue accounting for it, before admitting replacements. Add a real
coordinator-crash-with-live-workers regression and cancellation-after-restart
proof. Extend qualification for this path; the existing transaction-exit corpus
does not exercise it.

## CR16.5-02 — High: terminate sibling workers after the run becomes terminal

Location: `infra_automation/coordinator.py:364`.
AC4/AC7 require bounded execution with finite deadlines; AC2 requires terminal
state to describe the retained execution correctly.

A permanent result from one step calls `stop_run`, which terminalizes the run and
sets its other active attempts to `cancelled`. In the same tick, the heartbeat
branch handles only `claimed`/`running` rows. A cancelled sibling falls through
without a heartbeat or a worker cancellation call. The terminal run disappears
from candidate queries and `cancel_requested` is false for ordinary failure, so
neither candidate deadline handling nor `_observe_cancellations` cleans it up.
Its handler can run indefinitely and retain a worker slot beyond both deadlines.

Reproduction used a valid published two-root uploaded workflow, actual guarded
SQLite claims/start and a controlled worker port. After one permanent failure:
run=`failed`, failure attempt=`failed`, sibling=`cancelled`, owned step=`blocker`,
cancel calls=0. After 65 additional ticks advancing ten seconds each, 50 seconds
past the run deadline and 350 past the attempt deadline, the sibling remained
owned and there were still zero cancellation calls. Shutdown cleaned the port.
Scratch probe: `/private/tmp/s165_terminal_sibling_repro.py`.

Required fix: explicitly stop every owned process whose run/attempt is terminal,
missing, or no longer valid, retaining the slot until termination is confirmed.
Preserve uncertain external semantics. Add a failed-sibling/blocking-sibling
regression that proves process-tree cleanup and subsequent worker-slot reuse.

## CR16.5-03 — Medium: advance the scheduler beyond the oldest 100 candidates

Location: `infra_automation/coordinator.py:275`.
AC4 requires other ready work to progress; AC7 permits project/global queues
larger than this fixed selection window.

Every tick orders by the same sequence and applies `LIMIT 100` without a cursor,
rotation, or eligibility filtering. An old quota-blocked prefix can continually
hide later eligible workflows/projects, including their timeout processing.

Reproduction stayed within all configured quotas: `workflow_active_runs=1`, four
workflows with one active and 24 queued runs each (100 candidates), followed by
an eligible fifth workflow (101st row). Project totals were four active and 97
queued, below project limits. After three ticks, the fifth run was still queued.
Calling `_schedule` for that exact run immediately promoted it to running,
confirming eligibility rather than another policy denial.
Scratch probe: `/private/tmp/s165_review_starvation.py`.

Required fix: use bounded, advancing or fair candidate selection so blocked early
rows cannot indefinitely exclude later eligible work and deadline cleanup. Add a
regression beyond the 100-row window, including separate workflow/project quotas.

## CR16.5-04 — Medium: preserve retryable worker persistence/backpressure failures

Location: `infra_automation/local_workers.py:213`.
AC5 requires finite retries for declared-safe local failures; AC7 requires explicit
backpressure rather than falsely classifying temporary storage denial as a
permanent handler failure.

The wrapper catches every exception outside external intent and sends
`permanent_local_failure`. This includes temporary SQLite failures and the
engine's own 429 capacity/backpressure error while registering or committing a
successful handler output. The parent consequently fails the run after the first
attempt, even when `retry_safe=True`, bypassing bounded retries/output adoption.

Reproduction called the actual wrapper with a valid claimed attempt and successful
typed handler, injecting `LifecycleError(429)` exactly once at `register_upload`.
The injected boundary was called once. The wrapper emitted
`permanent_local_failure`; actual coordinator completion left run=`failed`,
attempt=`failed`, retry_safe=True, attempt_number=1.
Scratch probe: `/private/tmp/s165_review_worker_backpressure.py`.

Required fix: distinguish retryable local infrastructure/backpressure errors from
deterministic validation/handler failures. Preserve external-unknown and authority
revocation handling; do not blindly retry every exception. Test transient upload
and output-persistence failures, including recovery/adoption of already committed
output within the original deadline and attempt limit.

## CR16.5-05 — Low: correct the public lease visibility documentation

Location: `docs/infra-automation/engine.md:44`, compared with
`services/infra_automation_engine_service.py:297` and `StepView`.
The operator/API documentation must agree with the declared consumer contract.

The guide says leases never appear in public responses, but `StepView` deliberately
includes `lease_until` and `_step_view` serializes it. This is not a secret nonce
or an authorization bypass. Correct the guide to distinguish public lease metadata
from private ownership capabilities, consistent with the existing typed contract.
